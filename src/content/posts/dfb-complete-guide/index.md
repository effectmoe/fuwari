## 0. はじめに — この記事の地図

### 0-1. ぼくが感じている違和感

ここ数年、ぼくは同じ違和感を何度も持ち帰ってきた。

- AIにプロンプトのテクニックを覚えるほど、「これって何のスキルなんだろう？」と虚しくなる。
- 「AIに仕事を奪われる」と言われるけれど、じゃあ何を身につければ生き残れるのかは誰も言わない。
- 「自分で考える力が大事」と言われ続けてきたけれど、AIが3秒で答えを出す時代にもそれで本当に通用するのか。
- コンサルで使ってきた SWOT・3C・ロジックツリーをAIに投げると、自分が30分かけたものを3秒で返してくる。フレームを覚えた時間は何だったのか。

これらは別々の悩みに見えて、原因はひとつだ。

**人間に求められる能力が静かに、しかし決定的にスライドした**のに、ぼくらはまだ古い能力の延長で生きている。

## 1. 能力のスライド — DFBが立つ土台

DFBを語る前に、ぼくが一番伝えたい命題から先に置く。**能力のスライド**だ。

### 1-1. 2024年までと2025年以降の能力マップ

2024年までの世界で「知的労働者に求められた能力」をぼくは3つに整理している。

- コミュニケーション力（人と話す）
- PC操作（道具を動かす）
- **自分で考える推論力**（頭の中で答えを出す）

2025年以降の世界で求められる能力はこう変わった。

- コミュニケーション力（人と話す）— 同じ
- PC操作（道具を動かす）— 同じ
- **AIに考えさせる「枠」を作る力＝構造化能力**

3つめだけが入れ替わっている。**推論はAIに、構造化は人間に**、と圧縮できる。

### 1-2. 「推論はAIに、構造化は人間に」

なぜ推論がAIに渡ったのか。理由は3つしかない。

- **速い**：人間が30分かける推論をAIは3秒で出す。
- **安い**：人件費と比べて桁違いにコストが低い。
- **疲れない**：24時間動ける。土日も祝日もない。

この3つが揃った相手に「自分で考える」で勝負しても勝てない。だから人間に残る仕事は、**AIに「正しく」考えさせる枠を作ること**になる。これがDFBの存在理由だ。

### 1-3. SWOT・3C・4Pは「道具の1つ」になった

ぼくはコンサル時代、SWOT・3C・4P・5Force・MECEといったフレームワークを覚えるのに時間を使った。当時は「フレームをいくつ知っているか」が勝負だったからだ。

でも今、AIに「うちの会社のSWOTを書いて」と頼めば3秒で出てくる。**フレームに当てはめる作業はAIの仕事**になった。

人間に残された仕事はその一個上、**「今このカオスには、SWOTを使うべきか、表にすべきか、IF-THENにすべきか、それとも新しいフレームを作るべきか」を判断すること**だ。

つまり構造化スキルというのは、SWOT・3C・4P・5Force・MECE・IF-THEN・JSON-LDといったフレームを**包含する上位概念**にあたる。フレームを覚えるのは構造化スキルの**入口（L1）**で、本当の価値は**フレームを選ぶ・改造する・新しく作る（L3〜L4）**にある。

これが次の章「4階層」の話につながる。

## 2. 構造化スキルの4階層 — どこを目指すか

「構造化スキル」と一口に言っても、レベルがある。ぼくは4階層に分けている。

### 2-1. L1 知る → L2 使い分ける → L3 改造する → L4 新フレームを作る

| Level | スキル | 具体例 | 主にできる人 |
|---|---|---|---|
| **L1** | 既存フレームを**知っている** | SWOT・3C・4P を暗記している | MBA教科書を読み終えた人 |
| **L2** | 既存フレームを**使い分ける** | 「これはSWOTより5Forceだ」と判断できる | コンサル新人 |
| **L3** | カオスに応じて**最適フレームを選び、改造する** | 「SWOTのSとWに時間軸を足して4Dにする」 | コンサル中堅以上 |
| **L4** | カオスに合わせて**新しいフレームを作る** | DFBを設計するレベル | 理論家・経営者 |

DFBが目指すのは**L3 への到達**だ。L4は天才の領域で、ぼくも毎日 L3 と L4 の境目を行き来している。

### 2-2. AIに代替されるのは L1・L2 まで

ここが残酷だが、はっきり書く。AIに代替されるのは**L1・L2 まで**だ。

- 「SWOTを書いて」→ AIが3秒で出す。**L1の暗記は要らなくなった**。
- 「うちの会社のSWOTは？」→ AIが既存知識から3秒で出す。**L2の使い分けも代替できる範囲が広い**。
- 「うちの業界、SWOTじゃ説明しきれないから新フレーム作って」→ ここでAIは止まる。**人間の経験・違和感・暗黙知が必要になる**。

つまり、フレーム集を覚えるだけの講座やビジネス書は**もう商品にならない**。Google検索で出てくる無料情報と差別化できない。

### 2-3. 「当てはめ」より「目利き」が核

L3・L4 を支えているのは3つの「目利き」だ。

- **抽象度感覚**：今この問題を「個人レベル」「組織レベル」「業界レベル」のどの粒度で扱うべきかを瞬時に判断する感覚。
- **違和感察知**：作った構造に対して「これ、何かおかしい」と気づける感覚。1サイクル目を完璧にやろうとせず、回しながら違和感を拾う。
- **フレーム改造力**：既存フレームを「ここに時間軸を足す」「この軸を入れ替える」と改造できる力。

| 項目 | 当てはめ（誰でもできる） | 目利き（あなたの強み） |
|---|---|---|
| 入力 | 既知のカオス＋既知のフレーム | 未知のカオス |
| 必要なもの | フレーム集 | 経験・抽象度の感覚・違和感 |
| AIに代替されるか | **YES**（GPTが3秒で出す） | **NO**（人間の暗黙知） |
| 売れるか | 売れない | 売れる |

DFBが鍛えるのは、ここで言う「目利き」のほうだ。フレーム集の暗記ではない。

## 3. 系譜 — DFBはどこから来たか

DFBはぼくが突然思いついたメソッドではない。60年以上続く**知的歴史の延長線上**にある。

### 3-1. 構造化PGからDFBまでの60年

```
1960年代  構造化プログラミング（Edsger W. Dijkstra）
              ↓
1980年代  オブジェクト指向プログラミング（Alan Kay）
              ↓
1990年代  デザインパターン（GoF：Gang of Four）
              ↓
2000年代  ドメイン駆動設計（Eric Evans）
              ↓
2025年〜  DFB構造化メソッド（AI時代版・シュ コウメイ）
```

この系譜を貫く思想はひとつ。「**現実世界を、適切な抽象度でモデル化する**」ことだ。

- 1960年代は「プログラムの流れ」を構造化した。
- 1980年代は「データと振る舞い」を一体化して構造化した。
- 1990年代は「再利用できる設計パターン」を構造化した。
- 2000年代は「ビジネスのドメイン知識」をコードに反映する形で構造化した。
- そして2025年、ぼくは「**現実世界の塊そのもの**」を、AIが扱える形に構造化する技法としてDFBを提唱している。

つまり、DFBは IT の世界の中で発達してきた「構造化」を、コードの世界から**現実世界全体に拡張した**メソッドだ。

### 3-2. OOP（オブジェクト指向）との対応表

エンジニア出身の人にとって、DFBが一番腑に落ちるのは OOP との対応で見せたときだ。

| OOP の概念 | DFB（現実世界版） |
|---|---|
| オブジェクト（属性＋振る舞い） | カオスを「要素 + 関係」でモデル化する |
| クラス | 構造化フレーム（SWOT・3C・IF-THEN 等） |
| インスタンス化 | フレームに具体カオスを当てはめる |
| 抽象化 | 「個人 / 組織 / 業界」のどの粒度で構造化するか選ぶ |
| カプセル化 | 「事実 / 感情 / 影響範囲」を分離して扱う |
| 継承 | 既存フレームを拡張して新フレームを作る |
| ポリモーフィズム | 同じカオスを別フレームでも表現できる |

OOPを知っている人にとっては「ああ、現実世界もオブジェクト指向で書けるってことか」で一発で伝わる。

### 3-3. なぜ「現実世界に広げた」と言えるのか

コードの世界の構造化は「コンピュータが処理しやすい構造」を作る作業だった。DFBは「**AIが処理しやすい構造**」を作る作業として、それを現実世界に持ち込んでいる。

- 会議の議事録、商品紹介、社内会話、コンサル提案、教育カリキュラム — どれも「塊（カオス）」のままだとAIに渡せない。
- これらを Decompose（分け）・Frame（枠取り）・Build（組み立て）の3ステップで翻訳すれば、AIが消化できる形になる。

だからDFBは「思考のフレームワーク」ではない。**経験を AI に渡せる形に変換する一連の手順**だ。

「現実世界を OOP で書く」と言うとピンと来ない人にも、「**人の経験を AI に渡せる形に変換する技術**」と言えば伝わる。同じ話を別の言葉で表現しているにすぎない。

## 4. DFBサイクル — 3ステップの循環構造

ここからが本題だ。DFBの**3ステップ**を1枚絵で見せる。

### 4-1. Decompose（分）／Frame（枠）／Build（組）の全体像

```
   ┌─────────────────────┐
   │ 1. Decompose（分）   │  カオスを要素に分ける
   │   = 因数分解         │
   └──────────┬──────────┘
              ↓
   ┌─────────────────────┐
   │ 2. Frame（枠）       │  どの枠で見るか選ぶ
   │   = フレーミング     │
   └──────────┬──────────┘
              ↓
   ┌─────────────────────┐
   │ 3. Build（組）       │  実際に組み立てる
   │   = ビルド           │
   └──────────┬──────────┘
              ↓
       違和感あり？  ── YES → 1へ戻る
              ↓ NO
            完了
```

1つずつ言葉を足す。

- **Decompose（分）**：頭の中の塊やモヤモヤを、いくつかの要素に分けて取り出す。言語化されていなかったものを、言語化できる単位まで落とす。
- **Frame（枠）**：取り出した要素を、別の角度・別の文脈で枠取りし直す。「これは何の問題か？」「この判断は何を最大化しているのか？」を問い直す。
- **Build（組）**：新しい枠で要素を組み立て直し、AIが消化できる入力にする。そしてAIの出力を、人間の経験で見直す。

### 4-2. PDCA・OODAとの位置づけ

ビジネス書を読む人にとっては、PDCAやOODAと比べたほうがイメージしやすい。

| メソッド | 構成 | 目的 |
|---|---|---|
| **PDCA** | Plan / Do / Check / Act | 業務改善のサイクル |
| **OODA** | Observe / Orient / Decide / Act | 意思決定のサイクル |
| **DFB**（ぼく提唱） | **Decompose / Frame / Build** | **AI時代の構造化のサイクル** |

PDCAは「業務改善」、OODAは「意思決定」のために設計された。DFBは「**AIに渡す**」ために設計されている。

3つは敵対しない。DFBの **Decompose** の中で OODA の Observe を使ってもいいし、Build の後に PDCA の Check を回してもいい。**目的が違うので入れ子で使える**。

### 4-3. なぜ「サイクル」であることが重要か

DFBで一番大事なのは「**1回で完璧に作らない**」ことだ。

- 1サイクル目はだいたいズレる。それでいい。
- 組み立てたあと「何かおかしい」と違和感を感じる。
- そこで Step 1（Decompose）に戻る。
- 違う角度で分け直し、違う枠を選び、組み直す。

これを2〜3周回すと、現実のカオスに耐える構造になる。**失敗を含めて学習する適応的プロセス**だ。1回で完璧を目指すと、フレーム原理主義（9章C）に陥る。

ここまでが「DFB全体像」の説明。次の章から、サイクルを**回す前に何を宣言するか**（Step -1 と Step 0）に入る。
